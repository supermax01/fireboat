# Release procedure (design; no release is authorized)

The current `@fireboat/gateway` / `fireboat` build is a private, synthetic-only,
local-stdio candidate. [The release plan](../proposals/release-plan.md),
[packaging design §8](../proposals/m3b-s8s9-design.md#8-supply-chain-and-release-workflow-design)
and [current status](M3B-STATUS.md) define its remaining gates. A generated packet
records observations; it grants no publication permission. Historical host/backend
evidence does not certify a changed tar. No SMART, clinical readiness, vendor-wide
support, unaided ten-minute onboarding or general protocol claim follows.

## Freeze and local acceptance

Root integrates reviewed code and mutation entries, resolves B2's ≥200 independent
counted cases, checks docs/contracts/catalog, isolation, both-era evals, demos and
controls, then runs full local checks, independent review and the official root-run
14-shard mutation aggregate. Diagnostics and a stale aggregate are insufficient.
Record exact source inputs, commands, toolchain, output hashes and disposition.
Freeze the final claims and limitations with the candidate. No CI runs during these
development steps. This slice does not change `ci.yml`.

Root builds a new private stage with `npm run stage:package -- <absolute-new-stage>`.
Pack **that stage**, with `npm pack --ignore-scripts --json --offline <stage>
--pack-destination <new-pack-directory>`; save the unabridged JSON. Verify it with
`npm run verify:package -- --tar <tar> --pack-json <json> --stage <stage>` before
extraction. Keep the tar's own hash outside the tar. Inventory acceptance never
means silently regenerating the approved inventory for unexplained changes.

Install this exact verified tar into a new unrelated consumer directory using
ignored scripts and the approved production shrinkwrap. Copy its uninstalled
`quickstart/` tree into a separate fresh directory and install with its own locked
production `npm ci --ignore-scripts --omit=dev`. Cached acceptance installs can be
offline; a missing cached prerequisite is a failure, never an implicit fetch.
Collect `npm ls --omit=dev --all --long --json` and verify both installed trees.
No checkout source, tsx, symlinked dependencies, NODE_PATH or NODE_OPTIONS may supply
the installed product's launch. Run all three tasks × three arms × both eras
(18 runs, three independent tasks), missing-asset/runtime/stdout/lifecycle/seam
negatives and the final installed real-host smoke. Record actual supported cells;
unavailable Linux, Node or host cells stay unverified. These live package tasks
belong to the explicit installation gate, never ordinary mutation-unit judging.

The candidate and staged manifest remain `private:true`. **The owner must approve
the transition to a publishable stage** and the actual final repository URL and
metadata. That change requires a **new tar, hashes, inventory approval and affected
S9/S10 reruns**, before the final freeze and publication approval. The publisher
must never edit private/repository/version/mcpName or repack verified bytes.

## External packet and evidence binding

Use Node **24.22.0** and npm **11.19.1**. `release:manifest` reads actual installed
trees and invokes only offline `npm ls` and `npm sbom`; it never installs, compiles,
starts a listener, downloads an image, audits the registry or publishes.

```sh
npm run release:manifest -- \
  --stage /absolute/new-stage \
  --tar /absolute/pack/fireboat-gateway-0.2.0-alpha.1.tgz \
  --pack-json /absolute/pack/npm-pack.json \
  --gateway-install /absolute/fresh-consumer \
  --helper-install /absolute/fresh-helper \
  --npm-cli /absolute/node/lib/node_modules/npm/bin/npm-cli.js \
  --revision <40-character-base-revision> \
  --out /absolute/new-external-packet
```

`--revision` must match the checkout's base HEAD (read-only git check); the source-input digest also binds the
current staged source snapshot and release design files, including uncommitted
edits. It does **not** assert that those edits have been committed or that the
candidate is frozen. Root regenerates the packet after integration on the actual
frozen commit. Output can be external or under `artifacts/m3b-release/`, as the
slice contract specifies; it cannot be inside a stage or installation. Creation
is exclusive: an existing directory is refused.

The SBOM format is **CycloneDX 1.5 JSON**, generated by pinned npm with
`--omit=dev --sbom-format=cyclonedx --package-lock-only=false` against each installed
tree. The gateway SBOM excludes its empty consumer harness; the helper has its own
SBOM. Normalization removes npm's random UUID and timestamp and replaces npm's
project-root directory basename with its verified package identity for stable comparison.
The gateway's local tar distribution URL becomes the packet-relative `gateway.tgz`;
workstation paths are not retained in the published BOM.
Every component, dependency edge and SHA-512 integrity must match the independently
verified installed graph. No lock-only SBOM or checkout development tree supplies
an installed-production claim. The packet also hashes package-owned installed
files, and verifies installed license texts against the tar's inventory.

The packet contains the exact tar/npm JSON, regular-file inventories, shrinkwrap,
helper lock, both canonical trees and installed-file inventories, both SBOMs,
machine/readable license inventories, source inputs and `s10-handoff.json`.
`release-manifest.json` hashes every companion file. Its binding covers the tar,
shrinkwrap, trees, helper files/lock, licenses, compose, config, seed, contract,
runtime/profile JSONs, Node/HAPI pins, source snapshot and actual collector cell.
The manifest is external and does not hash itself. Config files contain the
already-approved synthetic fixture tuple; keep the packet restrictive, and do not
copy resource bodies, fixture identifiers or credentials into ordinary logs.

Root can attach reviewed reports with `--reports /absolute/reports.json`:

```json
{
  "schema": 1,
  "reports": [{
    "gate": "local-check",
    "status": "passed",
    "binding": { "copy": "the complete exact manifest.binding object here" },
    "evidence": [{ "path": "check.log", "sha256": "actual 64-character SHA-256" }]
  }]
}
```

This is a shape example, not accepted evidence. `binding` must be the complete
binding object; evidence paths are regular relative files under the reports file's
directory. Unknown/duplicate gates, missing evidence, changed evidence bytes and
partial or old bindings refuse. In particular `s9-release-binding` refuses reports
from another tar, shrinkwrap, helper, compose or config. Gate names are exported as
`GATES` from the generator. With no reports, every external gate is `missing`.
Reports are root-reviewed attestations of actual checks, not test execution or
cryptographic certification by this script. Passed historical Markdown records
are explicitly historical-only. A current binding is necessary but does not make
an unauthentic report trustworthy. Keep actual audit findings, tool/database date
and disposition; this offline generator claims no current clean audit.

## S10–S11 handoff

S10 consumes `s10-handoff.json`, verifies every referenced byte and installs from
the **same tar and locked dependencies**. It must not compile checkout source or
run a lifecycle rebuild in OCI. Hash changes invalidate affected reports and
require new accepted evidence. The helper remains a separate dependency tree.

Node `24.22.0-bookworm-slim` index and linux/arm64/amd64 children come from the
repository's dated packaging evidence, whose own hash is recorded. They are
metadata pins, not locally acquired or executed image proof. Missing Node config
descriptors, layers, acquisition and native execution remain explicit. HAPI's
packaged backend evidence supplies separate index, child and config hashes; image
IDs are not interchangeable with those digests. The current helper recipe is
linux/arm64; other HAPI/platform cells require their own evidence.

The handoff pins the packaged host compose, data and config templates. It emits
host and container config files from one synthetic config, changing only the
literal loopback source port **18080 → 8080**. The S10 compose itself is **missing**,
with a null hash. Its required topology is `network_mode: service:hapi`, only
HAPI published on `127.0.0.1:18080:8080`, no MCP port and no host.docker.internal
workaround. Numeric UID/GID 1000:1000, read-only root, dropped capabilities,
no-new-privileges, negative egress/proxy/redirect checks, attached-stdio tasks and
lifecycle require actual tests. OCI layout digest, image SBOM, base scan and
signature/provenance verification stay open until observed. Do not treat these
declared requirements as passed execution evidence.

S11 owns its separate preregistered natural corpus and measurement freeze. Freeze
all measurements after identity/artifact changes; report C.1–C.3 and unrun cells
honestly. Quickstart data and npm success cannot substitute for heldout measurements.

## The one release verification CI run

The owner chooses restored Actions billing or approved public-repository runners.
After all final bytes, claims, local evidence and owner decisions are frozen,
root requests the **one manual S12 verification run on that frozen candidate**.
It supplies Linux package unit/stage cells (through `npm run check`), shard cells,
Node 24.21.0/24.22.0/26.10.0 cells, live HAPI/Medplum and the pinned Linux
container token measurement that local evidence cannot supply. It does **not**
supply a Linux installed-package cell: `ci.yml` never runs
`test:package-installed`, and its x64 runners cannot run the linux/arm64-only
HAPI recipe. That cell stays unverified until the installed-artifact job below is
implemented, approved and run. A matrix declaration or historical green run
supplies no pass. The final packet binds the actual run ID, public repository,
head revision, workflow, conclusions, logs, artifact bytes and all input hashes. A failed or
changed candidate remains unreleased; the owner decides a newly frozen candidate
and any further CI authorization. No automatic dispatch or repair loop is implied.

G-BACKEND must be satisfied for the actual scoped claims; its old narrow HAPI
qualification proves no sort or continuation behavior. G-HUMAN requires an actual
person's named-file review of the isolation core and final claims, with findings
and disposition. B2, S10/S11, final installed-host evidence, redistribution review,
current audit disposition and independent model review remain separate gates.

## Publication design and owner acts

[release-npm.yml](../.github/workflows/release-npm.yml) is **design only**:
`workflow_dispatch` is its sole trigger, both its jobs are unconditionally disabled,
and each keeps an exit-1 interlock even if that condition is edited. It has no
executable publisher and no executable installed-artifact job. Nothing runs on
push, tag, release or pull request. Before enabling it, the owner approves a reviewed implementation with full-commit-pinned actions,
GitHub-hosted ubuntu-24.04, exact Node/npm, minimal `contents:read`, and
`id-token:write` only in the protected `npm-alpha` publish job. The owner configures
required reviewers, no self-approval/bypass, ref restrictions and npm's exact
repository/workflow/environment trusted-publisher binding. This setup is not
proved by committing YAML.

Its `installed-artifact-design` job is the designed Linux installed-package cell,
and the publisher `needs` it. On GitHub-hosted `ubuntu-24.04-arm` with
`contents:read` only, a future implementation would take the same approved
commit, tar SHA-256 and packet artifact ID. It would hash the packet's tar, npm
pack JSON, inventories, helper lock and timing wrapper before use and fail on any
missing or mismatched input. Then it would pre-pull the pinned linux/arm64 HAPI
digest, prepare a helper-owned run on the runner's local daemon, and run
`test:package-installed` against those exact files. It must require
`PACKAGE_INSTALLED_OK` naming that tar and always run the installed helper's
`down`. Only that linux/arm64 / Node 24.22.0 cell could be recorded; linux/amd64
and other cells stay unverified. Enabling it, like the publisher, needs an
owner-approved reviewed implementation. No automatic trigger is added.

The future publisher checks the approved commit/version/tar SHA-256 and immutable
packet artifact ID, verifies every evidence hash and the exact successful S12 run,
then acquires that reviewed tar without repacking. The public package repository
URL must match the final public source/provenance. With separate final owner
approval it publishes only that path, ignoring scripts, with public access,
`alpha` dist-tag and OIDC provenance, without a long-lived npm token. The owner
must settle first-publish scope/account bootstrap: if OIDC cannot bootstrap the
new package, an owner-authenticated exception requires approval of those same
bytes. Never silently fall back to a token or pass credentials through chat.

After an approved publication, verify retrieved version/dist-tag, tar SHA-256 and
npm SRI, provenance subject and source revision, registry signatures, and a clean
installation of the retrieved tar; retain actual results. A design cannot prove
those future observations. A Registry manifest stays outside the npm tar;
`mcpName` metadata alone is neither a submitted entry nor proof of namespace control.

Each open decision/action below belongs explicitly to the **owner**:

| Owner act | Concrete input needed |
| --- | --- |
| npm scope control and package/publishing principal | Actual `@fireboat` control, `@fireboat/gateway` availability and bootstrap method |
| Registry namespace | Confirm `io.github.supermax01/fireboat` control and final `mcpName` before the accepted pack; approve any later submission separately |
| Repository rename and public identity | Final repository name/URL, visibility, history inventory and full-history versus curated export |
| Seed/terminology and dependency redistribution review | `licenses.json`, verbatim licenses/required notices, Synthea data and code/display rights including LOINC, SNOMED CT and RxNorm; a generator source license alone is insufficient |
| Copyright, maintenance, contribution and security ownership | Holder, reporting contact/promises, contribution authority and accountable review budget |
| Engines floor and platform claims | Keep `>=24` or explicitly approve a coordinated floor change; advertise only passing cells |
| G-HUMAN | Named person, exact core/final-claims files, findings and disposition |
| Publishable transition | Approved manifest/repository metadata and new tar plus affected S9/S10 reruns |
| CI route and protected publishing setup | Billing/public visibility, the one frozen-candidate verification run, environment policy and trusted publisher |
| OCI acquisition and runtime execution | Exact Node/other image pins, separately approved downloads/platforms and disposable lifecycle |
| Landing, first public step and version | Merge/history choice, source preview versus alpha, final available prerelease version |
| Each publication | Exact reviewed source visibility change, tag, npm `alpha` tar, OCI digest push, Registry entry and announcement, separately approved |

The workflow/partner and later SMART-path choice, P8 validation, unaided-developer
study, comparison permission and maintenance/review budget from the release plan
remain owner-dependent. Comparative work stays prohibited without that permission.
Prior evidence of Synthea/Temurin acquisition is recorded historically; this
procedure does not grant a new download or container authorization.
