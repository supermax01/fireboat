# Security model

These are prototype boundaries, not a certification. fireboat is read-only, synthetic data by default (openly licensed de-identified research data is used only in local benchmarks, see [testing](TESTING.md#benchmarks-and-research-data)), local stdio and bound to one trusted patient. It exposes five implemented retrieval tools. There are no clinical writes, arbitrary mutating operations, placeholder clinical tools or hidden model calls.

## Patient and shared-instance checks

The patient binding comes from operator configuration, never from a model argument. Patient-linked searches carry the confinement pair. Every returned record, including contained resources, is re-checked under the patient or shared-instance policy.

The six searchable shared types are Practitioner, Organization, Location, Medication, CodeSystem and ValueSet. Medication, CodeSystem and ValueSet are catalog data and are searched across the whole source without a patient pair. Practitioner, Organization and Location are directory records and are delivered only when reachable (next paragraph). Shared predicates over withheld fields are refused at admission, including catalog prose, Medication lot numbers and identifiers without an explicit non-patient system and code. A Medication identifier predicate must also use a system on the operator's `privacy.sharedIdentifierSystems` list; with the default empty list every Medication identifier predicate is refused.

**Directory records are delivered only when reachable.** A Practitioner, Organization or Location is reachable when a record already delivered in this context for the bound patient names it by a literal reference to the configured source: `Practitioner/<id>` (a versioned form counts) or an absolute URL under the configured base. Delivered means read, searched, paged or replayed from a retained result. The reference is read from the record exactly as delivered: after withholding, redaction and `output.fields` or compact selection, including references inside its contained resources.

- **What grants nothing:**
  - a reference that was withheld;
  - a display-only or identifier-only reference;
  - a contained (`#id`), conditional, `urn:` or other-source reference, or one whose declared `type` disagrees with its literal;
  - any reference in an own record that was silently dropped, for example because it names another patient.
- **No chains.** Only the bound patient's own records grant. These never extend reachability: a delivered Location's `managingOrganization` or `partOf`, an Organization's `partOf`, the references of a directory record contained in an own record, and the references of a Medication found by a source-wide search.
- **Reads.** A `fhir_read` of an unreachable directory record returns `NOT_FOUND` before any clinical request, and the envelope is the same whether the record exists or not. A reachable id is read and judged by the shared-instance policy. A reachable id that does not exist costs one read, which shows only whether the patient's own records name it.
- **Searches.** A directory search is admitted only as `_id` alone, with every listed id reachable: no other predicate, no sort and no search without `_id`. Anything else is one `POLICY_DENIED` before anything is sent, the same envelope whichever id is unreachable. Refusals that do not depend on data (an unsupported parameter, modifier, chain or join) keep their own codes, and `_include` stays refused. A directory record the source returns that is not reachable, for example from a source that ignores `_id`, is dropped silently before it is judged.
- **Metadata.** Like any call, a refused one may first refresh the capability metadata; that is the only request it can cause.
- **The ledger.** The reachable keys share the bounded ledger of confirmed own-record targets above: 2,048 entries in all, see [limits](LIMITS.md). The same state boundary clears both: a change of capability revision, source identity or policy revision, a credential invalidation, or closing the gateway. Another context starts empty. When the ledger is full the least recently used entry leaves, whichever kind it is. An evicted directory key is simply unreachable again, so the rule fails closed; reading the own record that names it makes it reachable again.
- **Known limits.**
  - PractitionerRole is not classified, so a Practitioner named only through a PractitionerRole (for example from `Encounter.participant.individual` on servers that point it there) stays unreachable.
  - There is no chain to a parent organization or location, so the agent cannot name the hospital that owns a ward.
- The person-shaped silent drops under [shared records](#shared-records) still apply to reachable records.

**Residual: order-specific Medication records.** Medication keeps source-wide search, with its identifier and profile lists. Some sources mint order-specific Medication records, for example an IV mix published as a reference-only mix. On such a source, a source-wide Medication search can show that some patient received a particular mix, though not which patient.

**Reference filters on patient-linked searches.** A reference-valued search parameter on a patient-linked type accepts the bound `Patient/<id>`, a single explicit relative `Type/id` of a searchable shared type that the parameter's pinned R4 targets list, or explicit relative `Type/id` targets of a patient-linked type other than Patient (for example `encounter=Encounter/<id>`, `derived-from=Observation/<id>`, `based-on`, `part-of`). A patient-linked target is admitted only when that exact record has been authorized by this gateway, in this context and since the last state reset, as the bound patient's own record; the parameter's pinned targets must list its type; and patient-link parameters (`patient`, `subject` and the type's own link) never take one. A record already delivered to the agent counts, and so does a target confirmed by an earlier check. For a target not yet authorized in this context, fireboat first runs the ordinary confined search `<Type>?_id=<id>&patient=Patient/<bound>` (or `subject=`), through the same admission, transport, authorization and sanitizing path as any agent search; it never reads the target directly. Only when that search returns exactly the requested record, authorized as the bound patient's own, is the target remembered and the original search sent. Every other outcome (another patient's record, a record that does not exist, an own record withheld by policy, a type that cannot be searched, a malformed answer or an upstream error) gives the same `POLICY_DENIED` envelope, and the original search is never sent. Upstream errors here include timeouts, rate limits, credential failures and an interrupted check, so a refusal caused by one of them may succeed when retried. The check's own result is not shown to the agent. OR lists are allowed only when every part is such an own target, at most 4 distinct targets per search; each unconfirmed part costs one check, and shared targets stay single-valued. Checks run in the order the targets appear and stop at the first refusal. A target confirmed before a refused one stays remembered even though the search is refused, and the refusal's upstream call count shows how many checks ran; neither depends on whose record a refused target is.

This check departs from a stricter rule, that a reference target is never fetched to decide admission, which would refuse every target the agent has not been shown yet. The reasoning: the check is exactly a search the agent could already run itself through fireboat (`<Type>` with `_id`, confined to the bound patient), with the same confinement pair, the same per-record authorization and the same uniform answer for foreign and missing records, so it reveals nothing the agent could not already learn. Other refusals (modifiers, chains, too many targets, a foreign patient selector) still come first and send nothing. Bare ids, absolute, versioned, conditional and `urn:` forms, modifiers, chains, `_has`, includes, Group and unclassified types stay refused. The confinement pair is still appended, every returned record is still re-checked, and these filters are reported as not gateway-enforced. The remembered list is bounded (see [Limits](LIMITS.md)); an own record that was withheld, a read that returned `NOT_FOUND`, and any record other than the requested one on a check's page are never remembered.

A shared Medication record may carry identifiers only when every identifier is a `{system, value, use}` entry whose system is on `privacy.sharedIdentifierSystems` (empty by default, so by default any identifier leaves the record unclassified and withheld). Configuration refuses a listed system that overlaps a configured patient identifier system (exactly, ignoring ASCII case, or after URL serialisation) or that is one of a small built-in set of well-known US person identifier systems (SSN, MBI, Medicare, passport and driver's licence families). That built-in set is a floor, not a registry; operators still need to list their own patient identifier systems first.

A shared Medication with ingredients needs a fully coded `code`, with one narrow exception for reference-only mixes (for example an IV mix that a source publishes with no product code). A Medication with no `code` may carry `ingredient` only when it has at least one identifier and every identifier passes the listed-system rule above, and it has 1 to 32 ingredients, each with only `itemReference`, an optional boolean `isActive` and an optional `strength`. The `itemReference` carries only `reference`, exactly `Medication/<id>`: relative, unversioned, with no URL, `display` or `identifier`. The `strength` is a Ratio of two simple Quantities (a numeric value and optional `unit`, `system` and `code`; no comparator). There is no `itemCodeableConcept`, extension or modifier extension. Because the rule needs a listed identifier system, it cannot apply with the default empty list, so by default every uncoded Medication with ingredients stays withheld (with the shared signal). The reasoning for allowing such a mix: each ingredient only names another shared Medication, which is judged separately when it is fetched and is never fetched to decide this one; the only free text is an identifier value in a system the operator listed as a product system; and the `Medication/<id>` form cannot name a Patient. A Medication with a `code` that is not fully coded, and a free-text or uncoded compound without a listed identifier, stay unclassified.

A shared record may declare `meta.profile` entries only when every entry exactly equals one on the operator's `privacy.sharedProfiles` list (empty by default, so by default any declared profile leaves the record unclassified and withheld). A listed profile passes only the profile check: the field allow-list, the bans on extensions, modifier extensions and `meta.security`, the per-type constraints and the identifier rule all still apply. See [configuration](CONFIGURATION.md).

A read (`GET {type}/{id}`) is checked after the fetch. A foreign or unverifiable record returns `NOT_FOUND`. This is a uniform public unavailable response, not a claim that the record does not exist. A record of the bound patient that is withheld by policy also returns the same `NOT_FOUND`.

## Withheld records and unverifiable references

Each returned record of a patient-linked type gets one of three outcomes:

- **Delivered.** The record passes the strict patient check. Or the only problems are references in clinical-actor slots that cannot be verified, and those references are removed (see below).
- **Withheld with a signal.** The record's own patient link is the bound patient, but something in it cannot be checked, and that something does not depend on another patient's identity: for example an unclassified contained resource, an unreadable or unsupported reference, an unverifiable reference in a slot that may name a person of record, or a nesting or size budget overrun. The search page, its continuations and its retained result then report `coverage.state: partial` with the reason `RECORDS_WITHHELD_BY_POLICY` and a matching warning, never `query_exhausted: true`, and publish no total.
- **Withheld silently.** The record's own patient link is not the bound patient (another patient's record), or the record carries explicit evidence of another patient (a `Patient/<other>` reference, a declared Patient type, a contained Patient, a conditional query that mentions a patient, or an identifier that may name a person of record: one in a configured patient identifier system, compared with case and URL spelling folded, one in a well-known person identifier system such as a US SSN or Medicare system, or one typed as a person identifier by an HL7 v2-0203 code in any spelling of that code system or by person-like type text such as "MRN").

The signal is deliberately narrower than "any own record withheld". It is computed as if every other-patient identity in the record were the bound patient's, so its presence never reveals that a record mentions someone else (the isolation design's rule that caveats must not depend on suppressed evidence). Consequences: an own record withheld only because it names another patient, a shared record withheld only because it carries another patient's evidence, and a `fhir_read` miss all stay silent or `NOT_FOUND`, so a page can still be reported complete after such a drop. The signal never guarantees completeness. This identity independence holds only while every admitted search predicate matches delivered, non-withheld content, which is why full-text search is refused (see below). Searches of shared types are the one place where an admitted predicate can still match a withheld record; [Shared records](#shared-records) below says what that reveals and which shared records therefore stay silent.

### Shared records

On a search of a shared type (for example `Medication` or `Organization`), a returned shared record that fails the shared-instance policy is withheld with a signal: an unlisted field, extension, profile or identifier system, `meta.security`, a failed per-type constraint, an unclassified contained resource, or a nesting or size budget overrun. The page, its continuations and its retained result then report `coverage.state: partial` with the reason `SHARED_RECORDS_WITHHELD_BY_POLICY` and a matching warning, never `query_exhausted: true`, and publish no total. Without the signal, such drops would be silent and a page could publish a total lower than the source's. An uncoded Medication with ingredients that is not a listed reference-only mix (see [above](#patient-and-shared-instance-checks)), including every such Medication under the default empty identifier-system list, fails a per-type constraint and is signalled this way.

The same identity rule applies. A shared record dropped only because it carries evidence of another patient (a contained Patient, or a Patient reference that is not the bound patient) stays silent, and the verdict is computed as if that identity were the bound patient's, so the signal never depends on another patient's identity. A policy failure next to such evidence is still signalled, in both cases alike. On types whose field allow-list has no `contained` element (Organization, Location, Practitioner), any contained resource, a Patient included, is an unlisted field and is signalled whatever its identity. A shared record that contains one of the bound patient's records with an unverifiable clinical-actor reference is also signalled, because shared records are never delivered with parts removed. A `fhir_read` of a withheld shared record stays `NOT_FOUND`.

The signal has a cost: it confirms that an admitted search predicate matched a record that was then withheld. Searching a catalog type by a predicate, or a directory type by a reachable `_id`, can therefore show that a withheld record with that value exists, and can tell such a record apart from one that does not exist, which a `fhir_read` deliberately does not. For a content-neutral failure this reveals only values the policy would deliver if the record had no defect (for example the name of a Practitioner withheld for an unlisted extension). It would be a real disclosure for records withheld because of what they say about a person, so these stay silent, and a page containing one reads exactly like a page without it: a Location that is not an affirmed facility (residential, workplace, school, a patient's residence or untyped), an Organization with contact persons, and a record whose own identifiers may name a person of record (a configured patient identifier system, a well-known person identifier system such as a US SSN, or a person identifier type such as MRN). None of these tests depends on whose identity the record carries or on any identifier value. Like the drops caused by another patient, these drops can leave a page reported complete.

### Unverifiable references

On a record that is otherwise deliverable, a reference that cannot be verified (identifier-only, `urn:uuid`/`urn:oid`, or a conditional reference whose literal type is not Patient and whose query mentions no patient) is removed as a whole node, with its display, identifier, extensions and companions, and labelled `UNVERIFIED_REFERENCE_WITHHELD`. This applies only to clinical-actor slots: the element's declared targets must include Patient and at least one of Practitioner, PractitionerRole or Device, never `Resource`, and payee slots are excluded. Elements that may name a person of record, such as `DocumentReference.context.sourcePatientInfo`, `Coverage.subscriber`, `Coverage.policyHolder`, `Coverage.payor` and `Extension.valueReference`, are never redacted this way: the record is withheld with the signal instead. The redacted record must pass the strict patient check again, both before and after sanitizing, or it is not delivered. The primary patient link is never redacted.

Residual: free text elsewhere in a delivered record (notes, descriptions, `CodeableConcept.text`) can still describe the person behind a removed reference, as it could before. Identifiers in a configured patient identifier system inside typed non-Patient references and inside contained directory resources are delivered today; that existing gap is unchanged.

The [support matrix](SUPPORT-MATRIX.md) classifies 32 of the 147 FHIR R4 resource types: 22 patient-linked and 10 shared. Unclassified types are refused. These are resource types, not clinical sections. Documents are metadata-only.

**Medication administration and dispense, specimens, care plans, care teams, imaging studies and devices.** MedicationAdministration, MedicationDispense, Specimen, CarePlan, CareTeam and ImagingStudy are linked to the patient by `subject`, and Device by `patient`. They follow the same rules as the other patient-linked types: searches carry the `patient` confinement pair, every returned record and every contained resource is re-checked, a contained record of one of these types needs its own bound link, and an unverifiable clinician reference in a clinical-actor slot (for example `CareTeam.participant.member` or `MedicationAdministration.performer.actor`) is removed as described above. None of them has a reviewed compact recipe, so compact output falls back to the sanitized view with `COMPACT_RECIPE_UNAVAILABLE`. Some fields are always withheld, wherever a record of the type appears, root or contained:

- Device: `identifier`, `serialNumber`, `lotNumber`, `distinctIdentifier`, `manufactureDate`, `expirationDate` and `udiCarrier.carrierHRF` (`DEVICE_PRODUCTION_IDENTIFIER_WITHHELD`), `url` (`DEVICE_NETWORK_ADDRESS_WITHHELD`) and `contact` (`DEVICE_CONTACT_WITHHELD`). `udiCarrier.carrierAIDC` is base64 data and is withheld as a payload. The model-level `udiCarrier.deviceIdentifier`, issuer, jurisdiction, device name, model number, type, status and manufacturer are delivered.
- Device `parent`: the literal reference is delivered, but its `identifier` and `display` are withheld (`DEVICE_PRODUCTION_IDENTIFIER_WITHHELD`), because they can carry the parent device's serial number.
- ImagingStudy: `identifier`, `series.uid` and `series.instance.uid` (`DICOM_UID_WITHHELD`).
- Device and ImagingStudy `extension` entries, at every depth (`UNREVIEWED_EXTENSION_WITHHELD`): their content is unreviewed and can repeat a withheld identifier, for example the R4 Device DIN extension. `modifierExtension` is delivered.

Search parameters whose pinned R4 expression reaches one of these fields (equal to it, inside it or above it), and Device or ImagingStudy parameters over extensions, are refused with `POLICY_DENIED` before anything is sent, as filters and as sort keys: Device `identifier`, `udi-carrier`, `url` and `din`, and ImagingStudy `identifier`, `series` and `instance`. A test fails if a pinned parameter starts to reach a withheld field. Residuals: the same device or DICOM identifiers can still reach the agent inside references from other records (for example a `Reference.identifier` on `Observation.device` or `DiagnosticReport.imagingStudy`), some servers use a study UID as the ImagingStudy `id`, and free text such as `Device.note` is delivered. The isolation suite does not cover these seven types; they are covered by unit and gateway tests (`tests/added-patient-linked-types.test.ts`) only.

**Full-text search is refused.** On every patient-linked type, a search parameter with no pinned R4 expression is refused with `POLICY_DENIED` before anything is sent, as a filter and as a sort key. The main case is `_content`, which a source matches against the whole stored record, including fields the gateway withholds, removed references and narrative. Admitting it would let an agent confirm guesses about withheld values. The two reviewed exceptions are Patient `age` and `birthOrderBoolean`, which match only the birth date, deceased status and multiple-birth fields that are delivered. `_text` is never applicable, and shared types already refuse these parameters.

## Transport and continuations

- No tool argument accepts an arbitrary URL, host, header or raw request. `source` is a configured alias.
- Controlled transport accepts only literal loopback endpoints, ignores ambient proxy settings, meters compressed and decoded bytes, and applies deadlines and cancellation.
- Redirects are not followed. Redirects, external continuation URLs and unsafe links are denied or become labelled partial coverage.
- Cursors are opaque, expiring handles, not model-constructed URLs. Next links are validated before fetching. A full retention quota can evict the oldest cursor before its expiry; it then gives the same refusal as an expired cursor. Eviction only removes retained state: each store still holds one patient and one context ([Limits](LIMITS.md)).

An upstream next link must target the original resource path and retain every original constraint without changing or adding any. Two exceptions are allowed by design. A page reached through either is labelled `unverified_continuation`, and the label sticks for the rest of the chain:

- A server-root next link carrying `_getpages` may omit original constraints, but may never change or add one.
- An operator-declared continuation token, off unless `source.continuationTokenParameter` names it. The link must target the original resource path, never the server root. It must carry every original material pair with the same decoded value and multiplicity and no other predicate (reordering is allowed; re-spelling a value is not), keep `_count` unchanged and `_sort` unchanged or dropped, and add exactly one parameter with the configured name, whose decoded value is 1 to 2,048 characters in all, RFC 3986 unreserved characters followed by at most two `=` of base64 padding (a `=` inside a query value cannot start a parameter, because only `&` separates pairs and a pair splits at its first `=`), with no second token, no case variant of the name and no other paging mechanics (`_getpages`, `_offset`, `_cursor` and the like). Unlike the `_getpages` form it may never omit a constraint. The configured name may not be a known search or result parameter. Every page reached this way must itself pass the record checks described below, whether or not it carries a self link.

Any other invalid link makes the page non-continuable partial coverage.

### Pages without a self link

A search page's self link is the source's own statement of the filters it applied. A first page without one is refused with `UNVERIFIED_QUERY` unless the operator sets `source.selfLinkOptional` (off by default). Then the page is accepted only when no OperationOutcome on it reports an ignored or unsupported parameter, and every material constraint is either enforced by the gateway (patient confinement) or gateway-checked and holds on every authorized record of the page. Otherwise it is refused, just as it is when the setting is off.

Gateway-checked filters apply only to parameters whose pinned R4 expression is a simple element path; that classification is generated from the pinned R4 indexes (`packages/core/src/generated/r4-checkable-paths.ts`), never parsed at run time. They are: a token as `system|code` or a bare `code` on Coding, CodeableConcept, Identifier or code; a date with `eq`, `ge`, `le`, `gt` or `lt` on date, dateTime, instant or Period; a reference as `Type/id` or a bare id, compared with relative or same-source references; `_id`; and OR lists and repeated parameters of these. Everything else is uncheckable and refuses the page: every modifier, the prefixes `ne`, `ap`, `sa` and `eb`, `_lastUpdated`, the token forms `|code` and `system|`, string, quantity, uri and composite parameters, and any parameter whose expression is not a simple path.

A record fails a filter only when no reading of its value can match. A date without a timezone is read with 14 hours of slack either way, and a value of lower precision may be any instant within it, so a correct server is never refused at a boundary; codes are compared without letter case for the same reason. The cost is leniency: a record within 14 hours of a zoneless boundary, or with a code differing only in case, can pass. A record that fails a filter refuses the whole page as contradicted, and no record from that page is delivered. A record the gateway cannot judge (an unsupported variant such as Timing, an extension-only value, a reference to another source or an identifier-only reference) refuses the page too. Only records authorized for delivery are checked, so another patient's records on the page never change whether it is accepted or refused; twin tests pin this.

An accepted page is labelled `gateway_checked_records`, and each checked constraint reports `execution: gateway_checked`: every returned record was checked and none contradicted the filter. That is not proof that the source applied the filter. Every later page of such a chain is checked the same way, whether it arrives through the operator-declared token or an ordinary echoed next link, and is labelled `unverified_continuation`. The label proves membership only. Coverage is never `complete_for_query`, no total is published, no profile execution or order is claimed (`ORDER_UNVERIFIED` stays), and an empty page never reports `NO_MATCHES` and carries `FILTER_EXECUTION_UNVERIFIED`, because a source that ignored or rejected a filter looks the same as one with no matches. A source that silently leaves out matching records is not detectable with or without a self link. Pages that carry a self link are not affected by these settings.

The rule is general to any source without self links. fireboat still connects only to loopback and cannot sign requests for a cloud service itself, and no compatibility with any vendor service is claimed.

## Withholding, retention and logs

Inline `Attachment.data`, `Binary.data` and detected protected links are withheld before model output and retention, with labelled manifests. Attachment metadata remains available. Results are sanitized and projected FHIR-shaped JSON, not complete, unmodified source content.

Ordinary logs do not contain resource bodies, credentials or patient identifiers. The in-memory audit trail stores bounded metadata only; it is not a durable disclosure ledger. Outbound client credentials come from environment variables named in trusted configuration, never tool arguments.

The optional `privacy.patientIdentifierSystems` list matches absolute Identifier-system URIs exactly. It does no case folding, prefix matching or URI normalization. An empty or omitted list leaves patient identity in unlisted absolute-URI systems unwithheld. The policy for standalone shared-instance responses does not extend into the content of resources linked to the configured patient. See [configuration](CONFIGURATION.md) for the full matching rules.

## Exact values, coverage and response limits

Source decimal lexemes such as `7.0`, trailing zeros, exponents and unsafe integers survive parsing, projection, retention and final JSON serialization. A resource whose numbers cannot be preserved is refused rather than silently rounded.

Every result carries a coverage state, reasons (including `RECORDS_WITHHELD_BY_POLICY` and `SHARED_RECORDS_WITHHELD_BY_POLICY`, described above), each constraint with how it was enforced (by the gateway, by a qualified search profile, checked against every returned record of a page without a self link with none contradicting it, or unknown), and a query-evidence label. Exhausting pages is not presented as a complete clinical history. Errors say `query_evidence: "none"`. See [query evidence](QUERY-EVIDENCE.md).

A configurable byte ceiling applies to every tool result, errors included, not just upstream bodies. Since schema 0.4 it bounds the model copy, the larger of the text content and the compact `structuredContent` JSON, and a fixed invariant bounds the complete serialized MCP tool result, both copies included, at 3 × the ceiling + 4,096 bytes. Both are measured on the exact final result and checked again by the final delivery gate. JSON-RPC framing is measured separately. Which copy a host gives a model is not verified; a host that passes both would give it about twice the ceiling. See [Limits](LIMITS.md).

## Residuals and non-claims

Local stdio does not mean data stays on the device: an AI host may send tool output to its model provider. Unlisted identifier systems, authorized prose, timing and topology signals remain residuals. Nothing here establishes zero possible leaks, prompt-injection immunity, universal identifier redaction or a security certification.

No SMART authorization, authenticated remote MCP service, clinical or production readiness, clinical validation, regulatory compliance or general vendor compatibility is claimed. Synthetic results cannot establish those properties. The stricter patient-isolation test suite counts no cases, a mutation-gate result covers only the registered guards on the tree it ran on, and no independent human security or clinical review has happened. See [testing and evidence](TESTING.md).

Without its own recorded evidence, none of these is claimed either: SMART certification or enterprise-managed authorization; HIPAA, GDPR, CMS or ONC compliance or regulatory clearance; R4B, R5 or R6 support, US Core conformance or profile validation; full MCP protocol conformance, support for every MCP host or verified model-input behaviour; complete clinical history, proven absence, a verified latest result when sort order is unknown, or complete retained results; a durable disclosure ledger; token, speed or cost savings; npm, image or registry availability; review by AI models presented as human review; or anything about other FHIR MCP servers.

Report suspected vulnerabilities privately under the [security policy](../SECURITY.md).
